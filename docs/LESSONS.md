## #1 「最近打开」每次启动静默清空（2026-09-17）

- **现象**：首页画廊从未显示过任何真实记录；`recent.json` 文件明明存在且内容完好。
- **根因**：`RecentDocuments.persist()` 用 `.iso8601` 编码日期，`load()` 的
  `JSONDecoder()` 没设对应策略 → 解码整体失败 → `try? ?? []` 吞掉错误 → 归零。
- **沉淀**：
  - 代码修复 + 注释（`RecentDocuments.swift` load()）
  - 回归测试 `Tests/LumenKitTests/RecentDocumentsDecodingTests.swift`
  - 规则 `.claude/rules/persistence-coding.md`
- **后记（类级补修，见 #7）**：本条当时只修了**实例**——补上 iso8601 策略、加回归测试，
  却把「解码失败 → `try? ?? 空` → 下次保存覆盖原文件」这个**坏结构**留在了另外三处。
  真正封死同类坑的是 #7 的 `PersistFile.decodeOrBackup`。

## #2 图标书页路径画成「M / 蝶形结」（2026-09-17）

- **现象**：v2 App 图标与首页品牌字形里，摊开的书页渲染成两个交叉的细条。
- **根因**：贝塞尔控制点放在了端点的**另一侧**（镜像侧向时控制点没跟着翻），
  二次曲线反向交叉。SwiftUI `Shape` 与 CoreGraphics 都一样：控制点必须与
  弧线行进方向同侧。
- **沉淀**：`.claude/rules/branding-assets.md`（禁止手绘路径做图标，SVG 为唯一源）；
  `WelcomeView.swift` 里 BookPage 保留注释说明侧向与控制点同侧的原因。

## #3 图标光晕变成硬边圆盘（2026-09-17）

- **现象**：图标顶部的「光」渲染为边缘锐利的实心圆。
- **根因**：`NSGradient` 是**线性**渐变，没有径向衰减；想发光得用
  `CGContext.drawRadialGradient`。
- **沉淀**：v3 已整体改走 SVG 管线（radialGradient 语义直接可用），
  规则见 `.claude/rules/branding-assets.md`。

## #4 SVG 光栅化环境踩坑（2026-09-17）

- **现象**：`puppeteer.launch()` 反复失败——找不到浏览器、viewport 报错。
- **根因**：puppeteer 的浏览器缓存目录是空的（从未下载）；headless 模式参数
  因版本而异（新版本用 `headless: 'shell'` 且不需要 `executablePath` 指向不存在的路径）。
- **沉淀**：最终方案 `puppeteer-core` + 系统 Chrome + `headless: 'shell'`，
  固化在 `branding/render.js` 与 `.claude/rules/branding-assets.md`。

## #7 「解码失败静默清空 → 下次保存覆盖用户数据」是一类，不是一个点（2026-09-18）

- **现象**：`recent.json` / 阅读进度 / `memory.json` / `settings.json` 里的服务商配置，
  只要解码失败一次，就会被容错成空值，随后被下一次持久化**原样写回磁盘**——
  用户数据被一份「合法但空」的文件替换，且没有任何提示或日志可查。
- **根因**：`let x = (try? decode(...)) ?? 默认值` 把「**没有数据**」与「**解码失败**」
  压成了同一个结果，而「默认值」在实际写入路径上就等于「清空」。这是结构问题：
  同一形状在代码里有四处（LESSONS #1 只修了其中一处的实例）。
- **修法（类级，一处工具函数）**：`PersistFile.decodeOrBackup(data:type:fileURL:)`——
  解码失败时把原文件**改名**为 `<name>.corrupt-<时间戳>` 并 NSLog，返回 nil；
  调用方拿 nil 时**不把内存赋成空值**。改名（而非复制）是关键：原路径随即变空，
  后续任何 `persist()` 只能写新文件，**不可能**再覆盖用户原数据。
  - 四个调用点：`RecentDocuments.swift`（recent.json）、`ReadingStateStore.swift`
    （阅读进度）、`MemoryStore.swift`（memory.json，注意：旧「纯字符串数组」格式
    能解出来就是有效文件，**不得**误判为损坏）、`SettingsStore.swift`（settings.json）。
  - `settings.json` 的次级情形：逐字段容错会让「整份文件解得出、但 `providers`
    被吞成空数组」，文件级备份抓不到；故 `SettingsStore` 额外比对「磁盘上有几条
    providers」与「解出来几条」，命中才备份（判据见 `providersLookLost`）。
  - 编码侧的对称问题：`try? data.write` 失败同样无声，统一改走 `PersistFile.write`（失败 NSLog）。
- **沉淀**：
  - 工具函数 `Sources/LumenKit/Store/PersistFile.swift`
  - 回归测试 `Tests/LumenKitTests/PersistFileTests.swift`（备份生成 / 字节保留 /
    内存不写死空 / 旧格式不误判 / 服务商丢失才备份 / 键路径护栏）
  - 本账本条 + `docs/AUDIT-code-health-2026-09-17.md` P1-1 / P1-2

## #8 对不可复现的读数下断言，等于抛硬币（2026-09-18）

- **现象**：`--perf-report` 的 ③ 行（翻页二次遍历的进程常驻内存增量）在**同一构建、
  同一台机器**上反复跑，读出 −21 / −3.8 / +30 / +68 / +5.5MB——其中一次 +68 直接触发
  「≤ 24MB」的失败断言。这条断言时绿时红。
- **根因**：`phys_footprint` 是**进程级**采样，而这个跨遍增量由 PDFKit 内部渲染缓存
  （首次访问每页时建立、之后按自己的策略回收）主导；它先建还是先收、落到哪一档，
  不受我们这层控制。对一个由外部组件主导、时好时坏的量下断言，绿色不能证明没泄漏，
  红色也不能证明有泄漏——**比不打这个断言更糟**，因为它会给人「验过了」的错觉。
- **修法**：③ 降级为**信息性读数**（照打数字、不参与通过/失败计数）；
  「会不会持续增长」改由**确定性**判据把关——④ 缩略图缓存「滚完全本后仍驻留多少张」
  是可复现的（上限 160 vs 关掉上限 600）。同时保留 `--perf-thumbnail-unbounded` 开关，
  让「关掉优化读数必须变差」这条可证伪性成立。
- **沉淀**：规则「**读数的来源不在我们这层、又不可复现时，只能当读数，不能当断言**」；
  通道 `Sources/LumenApp/Reader/PDF/PDFPerfAudit.swift`（`--perf-report`）。

## #9 build.sh 的批量删除被守卫拦下，导致「构建静默失效」（2026-09-18）

- **现象**：`./build.sh release` 稳定返回非零，并打印一行和构建毫不相干的东西：
  `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":100,"threshold":50,
  "targets":[".../dist/Lumen.app"]}`；而 `dist/Lumen.app` 仍是旧的那份。
- **根因**：脚本用 `rm -rf "$BUNDLE"` 清旧产物再重建。本机的 safe-delete 守卫按
  「**一次删除的内容文件数**」计数（一个 `.app` 有上百个文件 > 阈值 50），把这条 `rm`
  拦下并让它返回非零；`set -e` 随即中断，后面的 `cp/codesign` 全没跑 → dist 保持旧值。
- **次生灾害更隐蔽**：调用方只看到「构建失败/非零退出」，很容易误判成「代码改坏了」；
  更糟的是**后续验证接着跑在旧二进制上**，读数全错还以为构建成功（本轮 #14 性能验证
  就实打实踩过：一度跑在旧 dist 上做对照）。
- **修法**：`build.sh` 改成「组装到唯一暂存目录 → 成功后 `mv` 换入」：
  1. 全程不碰 `dist`，编译/组装/签名/自检任一步失败，旧产物**原封不动**（原子性）；
  2. 换入只用 `mv`（同文件系统内即 rename），旧产物 `mv` 到 `dist/.trash`，
     **绝不 `rm` 一个 `.app`**——从根上避开守卫；
  3. 换入**前后**各校验一次写进 bundle 的「构建标记」，不新鲜就**非零退出**并明确报
     「dist 未更新」——「构建通过」本身也要能被证伪（README 硬约束 #8）；
  4. 失败与成功都走 `trap` 收掉暂存目录，`dist` 不留垃圾。
- **沉淀**：`build.sh`（暂存换入 + 构建标记 + `trap` 清理 + 证伪钩子
  `LUMEN_BUILD_SABOTAGE=stage|dist`）；排查步骤见 `docs/VERIFY.md` 第五节；
  规则 `.claude/rules/build-and-signing.md`。

## #10 「卡顿」要在**连续交互**里量，量法本身有三个坑（2026-09-18）

- **背景**：用户报「拖动分隔线抖、触控板滚动卡」。上一轮 `--perf-report` 量的是**单次**代价
  （一次翻页 / 一次整页光栅化），全绿——因为它答不了「连续动作里**每一帧**要重算几遍重活」。
  新增 `--jank-report` 通道专量后者。通道本身踩了三个坑，全都是「读数看着绿、其实没量到」：
  1. **ViewModifier 计数器不会每帧触发**。最初把计数做成 `.jankProbe(.containerBody)` 修饰符，
     结果所有 body 计数恒为 0。根因：SwiftUI 对「结构没变、修饰符值相等」的节点会复用上一次的
     `body(content:)` 结果，修饰符里的语句只在首次构造时跑一次。**必须写在视图 `body` 的第一条语句**
     （`let _ = Jank.tick(.xxx)`，就是 `let _ = Self._printChanges()` 那个惯用法）。
  2. **`PDFView` 不吃滚轮**。把 `CGEvent` 转成 `NSEvent` 投给 `pdfView.scrollWheel(with:)` 等于投给一个
     不接的人——页码与滚动偏移纹丝不动，计数全 0 还自称通过。真正消化滚轮的是它内部的 `NSScrollView`，
     得投给它。另外带精确增量的滚动会进「响应式滚动/惯性」，PDFKit 的页码变更回调**要等滚动落定**才发，
     投完立刻读计数同样全 0——要再等一段惯性滑行。
     还加了**方向自适应**：不同机器的「自然滚动」会翻转滚轮符号，写死方向在一半机器上滚不动。
  3. **拖动段的可用区间可能是退化的**。侧栏可见 + 最小窗口 920pt 时，AI 面板上限被阅读区保底压回下限 300，
     `range` 塌成 `300...300`——每步写同一个宽度，布局根本不重算，计数**假绿成 0**。
     通道现在会显式打印「可用区间仅 0pt…本段读数无效」。**任何「全 0 通过」都要先问一句：驱动真的动了吗。**
  4. **「主线程停顿低」不等于「没干活」**（最容易骗过自己的一条）。滚动段一度报「停顿 p95≈1.9ms、
     `PDFView.draw=0`、滚动不产生每帧重活」——**结论是错的**。两把尺子都是瞎的：
     停顿计时器只量主线程；`PDFView.draw(_:)` 只在「view 被要求重画」（frame 变化）时触发，
     而 PDFKit 的分页光栅化走内部文档视图的 **tiled/layer 路径**，根本不经过它。
     换成 **`getrusage` 的进程 CPU 时间增量**（含所有线程）一看就露馅：滚动 **752ms / 12.5ms 每步**，
     重活一直在做，只是在**后台线程**。定位工具本身也要有「与线程无关」的旁证；
     本通道现在会在「停顿低 + CPU 高」时显式打一行提醒，并已用「强制重绘」自检确认 draw 计数器没坏（`0 → 1`）。
  5. **「每步重活全 0」不一定是很轻，很可能是「合并链路根本没跑」**（本轮踩到，最隐蔽）。
     现象：**同一份 release 构建**，只换文档/窗口重跑，拖动段 `ReaderContainerView.body` 一次是
     `67(1.12/步)`、一次是 `0(0.00/步)`，而两次的「宽度扫过区间」自证都正常——看起来像随机抖动。
     根因有两层，缺一不可：
     - **自证不自证「布局」**。原来的拖动自证只打印「宽度 a→b」（那是**入参**，不是结果），
       证明不了「写真的变成了布局」。现在改成打印 **`写入 N 次 → 实际应用 M 次`**
       （`value` 真正改变的次数，只有它才触发布局）+ **合并节拍回调次数** + **容器重算次数**，
       并在驱动跑完后**先 `flushNow()` 坐实 pending、再等 3 拍**才取计数——0 才终于有了含义。
     - **`CADisplayLink` 会静默停发**。它的回调由 **CoreAnimation 驱动**；**窗口被判定为遮挡 /
       应用非激活 / 屏幕休眠**时一次都不回调。实测自证行直接摊牌：`显示刷新回调 0 次`、
       窗口 `occlusionVisible=false appActive=false`。后果不只是读数假绿——`pending` 永远等不到应用，
       **拖动期间面板根本不跟手**（一遮挡就坏）。这才是 A/B 之谜的答案：**与文档、窗口宽度都无关**
       （两次 `容器宽` 都是 1400pt），只取决于那一刻 CA 有没有驱动显示刷新。
- **元凶与修法**：定位到拖动时**每个指针事件 → 一次整页重光栅化**（`PDFView.draw=1.0/步`）。
  而指针事件率高于屏幕刷新率（触控板 90–120Hz、鼠标上千 Hz），一个显示帧里 3 个事件就是 3 次重光栅化。
  修法：把宽度写入**合并到每个显示刷新应用一次**（`LivePanelWidth`），屏幕本来只按刷新率显示，
  用户看不出差别，重活从「按事件率」降到「按刷新率」。
  **节拍从 `CADisplayLink` 换成主队列 `DispatchSourceTimer`(60Hz)**（见坑 5）：定时器只依赖主队列，
  与 CA/遮挡无关，不会「一遮挡就冻结」；`DispatchSourceTimer` 会合并补偿错过的触发，不掉帧时就等价于 60Hz。
  唯一放弃的是「与 vsync 严格对齐」——宽度是布局输入、不是播放中的动画，相位差不到一帧用户看不出来。
- **实测（本机，每帧模拟 3 次指针写入，release @本轮）**：
  - 合并前：`ReaderContainerView.body=3.02/步  PDFView.layout=2.80/步  PDFView.draw=2.80/步`，
    主线程停顿 p95=20.7ms、`>16.7ms` 占比 10%。
  - 合并后：`~1.0–1.3/步`（见下），p95≈2–3ms、占比 **0%**。
  - **证伪**（同一构建，`--jank-no-coalesce 1` 关掉合并）：`body=181(3.02/步) layout=147(2.45/步)`，
    进程 CPU 从 ~40ms/步 涨到 **90ms/步**——证明是合并本身在起作用。
  - **可复现性（同一命令各连跑两次）**：A（large.pdf 1400x900 thumbnails）`body=76(1.27/步)` / `64(1.07/步)`；
    B（text.pdf 默认窗口）`body=62(1.03/步)` / `69(1.15/步)`——两段落进**同一档**
    （修复前同一对命令是 `67` 与 `0`）。残余 ±10% 来自真实 CPU/步 的差异（A 的 120 页整页光栅化更重，
    40–52ms/步；B 22–25ms/步），不是测量噪声。
  - 进程 CPU（另一把尺子）：拖动 A 3121ms（52ms/步）、B 1352ms（22.5ms/步）；滚动 752ms（12.5ms/步，后台线程）。
  - ⚠️ **`ReaderContainerView.body` 的「每步均次」只在「应用次数 ≈ 步数」时才可读**：自证行会先判定
    `写入>0 / 应用>0 / 容器重算>0`，任一为 0 就打印「读数无效」，绝不让 0 冒充「很轻」。
- **滚动段的处置**：合成事件复现不了触控板连续惯性滚动，改为新增**被动监视** `--jank-watch 1`
  （正常运行、后台每 2s 落一行到 `/tmp/lumen-jank-watch.log`，用户用真机手势产生负载）。
  在此之前，**任何「滚动不卡」的结论都不得写进文档**。
- **沉淀**：`Sources/LumenApp/Shell/JankAudit.swift`（通道 + watch + 拖动自证）、
  `Sources/LumenApp/Design/LivePanelWidth.swift`（修法 + 三个自检计数）；
  读法与两通道分工见 `docs/VERIFY.md` 第四节「验证连续交互的卡顿」。
- **通法（比具体 bug 值钱）**：**「读数全 0 / 乱跳」时，先证伪「工具量到了没有」，再谈结论。**
  本轮连续三个坑（ViewModifier 恒 0、`PDFView` 不吃滚轮、合并链路没跑）都是同一个形状——
  不是被测对象变好了/变坏了，而是**读数链路本身断了**。规矩：给任何「0/低」配一条**独立的正向自证**
  （驱动真的动了、值真的应用了、计数真的会亮），自证不过就明说「本段读数无效」，绝不让 0 冒充「很轻」。

## #11 真机数据把滚动卡顿钉在 PDFKit 渲染，但三个旋钮逐个证伪（2026-09-18）

> 后续勘误（2026-09-27）：本节“卡顿只在 PDFKit”归因已被滚动期页码/视口发布的隔离实验推翻；本节仅保留当时三项渲染开关的单变量对照。当前结论和真触控板验收规则见 [PDF 面板与空白复核](PDF-PANELS-20260923.md)及 [VERIFY](VERIFY.md)。

- **背景**：`--jank-watch` 真机数据（2 秒一窗）活跃段 **进程 CPU 2 秒烧 5.9–6.8s ≈ 3 个核**，
  而同一窗口里我们这层所有 SwiftUI 计数器（`body/ai/side/thumbBody/update/layout/draw/thumbR`）
  **全 0 或个位数**。两件事合起来只说明一件事：**卡顿在 PDFKit 的渲染 / 合成里，不在视图树里**。
- **做**：①把 `--jank-report` 的合成驱动加重到接近真机（`--jank-scroll-delta` 30→**1900**，
  实测饱和点 ≈ 适宽倍率下一整页高度）；②主指标换成 **CPU/步（`getrusage`）**，主线程停顿仍报
  但**不许**用它下「不卡」结论；③对三个旋钮（`pageShadowsEnabled` / `displaysPageBreaks` /
  `interpolationQuality`）**逐项单变量证伪**；④改渲染后做同页同倍率**逐像素保真对比**。
- **结论：三个旋钮都省不下 CPU。** 交错重跑 3 轮取中位（`large.pdf`、delta 1900、120 步，ms/步）：
  基线 **17.7** / 关投影 19.1 / 关留白 18.9 / 插值 none 17.2 / 两个都关 19.9——
  差异全在 ±1.5ms 噪声内，且方向与「关掉更省」的预期相反。
  **关页面留白反而更费 ~1ms**（三轮均高于基线三轮，不是噪声）：页挨页贴在一起后，
  同样 1900px 的一步会跨过更多页，每步要光栅化的页内容更多。**瓶颈是 PDFKit 内部整页光栅化。**
  → **渲染默认回退原样**（`PDFRenderTuning.baseline`，与改造前逐像素一致）；旋钮 + 开关只留作复跑对照，
  不是待生效的优化。
- **两个方法论要点**：
  1. **合成驱动有天花板**：本机合成事件最多只到真机的 **~0.42–0.51×**（加重到饱和也够不到）。
     所以「与真机的倍数」当**参考**不当验收线——合成事件搓不出真机触控板那种连续惯性负载，
     这正是当初要做 `--jank-watch` 让真机出手的原因。驱动强度必须**自证打印**（CPU ms/步 与真机倍数）。
  2. **像素对比必须先量噪声地板**：同配置两次运行互比 **0.000%**（工具精确到像素）之后，
     「关投影 = **0.000%**（逐像素一致 → 这开关在本配置下压根不起作用）」与
     「关留白 = **17.4%**（页面上移 ~22px、页间分隔消失）」才是可信的。
     另外「关留白」的组合**重排更慢更不稳**：`--capture-delay 8` 抓到过「第 5 页 + 残缺拼贴」的中间态，
     到 14s 才落定成同一张图——这本身就给了「不该关它」的第三条理由。
- **第三个坑**：省 CPU 的对照实验要**交错重跑（round-robin）**，否则「后跑的更热」会被误读成「某旋钮更省」。
- **沉淀**：`Sources/LumenApp/Reader/PDF/PDFRenderTuning.swift`（三旋钮 + 开关 + 结论）、
  `PDFRenderAudit.swift`（钉死渲染状态供截图）、`tools/image_diff.swift`（逐像素对比）、
  `JankAudit` 的 `--jank-scroll-delta/-burst/-zoom` 与「驱动强度」自证行；读数表见 `docs/VERIFY.md` 第七节。

## #12 智能目录不能把模型猜测当作原书定位（2026-10-24）

- **现象与原因**：每页仅保留开头 260 字、最多抽样 160 页，会漏掉页中和未抽到页的标题；提示词又允许自拟主题标题、限制 20 字，并直接采用模型返回的页码。合法范围内的错误页码无法被越界检查发现。同页数文件替换也未失效。
- **现行做法**：PDF 逐页在独立后台文档中取标题候选，模型只选择候选 ID；标题和物理页由程序映射，长标题不截断，所有候选按输入/输出预算分批处理。EPUB 优先沿用目录锚点，一次导航携带锚点，不能先跳章再重载一次。未知 ID 整批失败，不补猜页码；缺正文先提示识别，不偷偷发起 OCR。
- **实测陷阱**：指定中文论文将“一”和顿号后的标题拆开，三个小节标题跨行；逐行检测会漏或截短。PDFKit 行选区的 bounds 可能包含相邻基线，不能把 union 高度直接当字号；本轮结合原始文字范围、首字位置、实际字号及相邻行处理。仅凭字体或正则仍有正文候选，模型负责筛选，不能把候选计数当目录准确率。
- **防回归**：文件/算法版本在缓存载入、生成结束、跳转及摘要回写时核对。旧缓存不显示为已核验，也不自动删除；取消摘要用任务令牌清理，旧任务不能清除新任务的状态。9 项新测试覆盖伪造字段、未知 ID、450 项全量分批、缓存替换、取消、缺页、双语题名和同页多标题选中；指定 9 页中文论文的 13 个标题及位置由原文清单独立核对。真实模型首轮多选了文末英文题名，后补“英文题名—罗马字作者—Abstract”局部版式排除，并保留 Chapter/Part/Section 标题；该启发式不保证所有双语版式均识别。点击父标题时，不能仅凭页码把同页最后一个子节标成选中，应暂存用户实际点击 ID。详见 `SmartOutlineHeadingTests`、`SmartOutlineIntegrationTests` 与本轮 VERIFY。

- **API与网页可用性分开验证**：应用内首次点验收到GitHub REST 403；同机curl请求仍200，不能用终端成功证明应用网络成功。应用URLSession诊断明确返回API配额耗尽，未归咎代码或让用户填令牌。补官方latest发布页重定向＋同版SHA256SUMS＋ZIP HEAD长度后备路径，实际后备检索通过；两条路径都不放宽签名核验。网络不可达仍就地反馈，不把它当无更新。
- **回归必须检查延后布局**：扩大测试时抓到24pt连续回答在Markdown完成后尾部没跟上；单独跑原套件通过，不直接归为偶发噪声。增加“文档高度回调→首次reconcile→延后clip修正”测试，旧代码稳定两处失败。布局标记原在首次reconcile末尾清空，后继修正被误判为用户上滚；改为有代次的两个主队列静默回合后清空，实际输入仍立即暂停，布局期间继续合并校正。实际验证收据和性能边界见 [本轮记录](verification/highlight-update-20261027/README.md)。

## 批注单向导出与个人笔记双向编辑要分开（2026-10-29）

## 首次文献笔记不依赖 Zotero 在线（2026-10-29）

首次写作不依赖 Zotero，但“先留空、60秒后再试”会让在线用户误以为关联失败。现优先读取可用题录，首次只短暂等待；耗时任务由 LiteratureLookupTasks 保留并供后台对账复用。确认无匹配后降为60秒重试，避免持续扫描大库；Zotero 启动通知清除等待并立即核对。在线走本地 API（附件列表须分页），离线从配置的 Zotero 数据目录以 SQLITE_OPEN_READONLY + 事务读取；数据库锁定时不复制、不强开，继续使用已缓存题录和 Markdown。真实附件路径必须完全一致，不能用同名文件关联。已知题录填空并更新此前自动填写的值，用户手改、自定义属性和已删除属性保留。期刊也必须更新持久映射，不能只刷新标题、作者和日期。

若初始记录先于页面落盘被 UI 观察，侧栏第一次读取可能失败；短暂读取错误与编辑冲突需分开，后续成功后清除读取错误，不保留“文件不存在”的过期提示。macOS `/var` 与 `/private/var` 测试比较使用真实路径。

## 不可读文件与跨窗口批注保护（2026-10-30）

JSON 读失败与文件不存在必须区分。仅在解码失败时保护原件仍有缺口：不可读但目录可写的文件可能先被当成默认值，再由原子保存覆盖。设置、记忆、快捷键、阅读状态、最近文档、会话和文献图谱统一使用 PersistFile.readJSONData；读失败登记写入阻断与恢复提示，空文件先备份。EPUB AnnotationStore 同时核对加载时原始字节，避免另一个窗口的新批注被旧快照覆盖；失败回滚内存编辑。回归覆盖实际权限拒绝、空文件、两实例交错保存。实测 Foundation 的 `.atomic` 写入可以通过重命名替换只读文件，不能把原子写当作权限检查；JSON 保存、文献页导出和属性保存均在写入前明确检查目标可写，失败不提前显示已同步，导出也不反复生成无效备份。

## 首页也必须使用一致主题（2026-10-30）

首页背景/文字来自阅读主题，原生控件却随系统外观，会形成浅色底上的深色图标和错误按钮前景。统一应用外观与阅读主题，强调按钮按背景相对亮度选择黑/白前景；五种主题均需检查，不能只测阅读窗口。
