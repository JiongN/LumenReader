# LumenReader 全面审计与修改记录

## 范围与结论

本次审计覆盖 SwiftUI 窗口与标签状态、PDFKit / WebKit 阅读链路、EPUB 解包与内链、AI 会话和翻译、持久化、更新与发布脚本、主要 UI 入口及工程目录。当前版本已修复会导致 EPUB 翻译失效、解包越界、持久化静默丢数据和发布误报成功的高优先级问题。2026-09-27 续审补齐烟测完成收据、EPUB 书内脚本边界、大型 PDF 的后台批注保存和 Swift 6 严格并发构建。PDF 流畅阅读仍是第一优先级；本轮只做自动化性能测量，不以其代替真实触控板验收。

审计不等于穷尽所有第三方 PDF / EPUB 变体、所有 macOS 小版本和真实网络服务。下文会明确区分已修复项与剩余风险。

## 主要发现与已实施修复

## 架构与 UI 评估

分层总体合理：`LumenKit` 承载可测试的核心能力，`LumenApp` 承载平台 UI 和控制器，每个文档由 `ReaderSession` / `ReaderBridge` 统一 PDF 与 EPUB 能力。最大的长期耦合点位于较大的 SwiftUI 视图、应用内诊断程序与主目标同编译，以及全局 AI 会话和窗口级文档状态之间的边界。它们目前不构成已知崩溃点，但会增加后续改动的回归风险。

UI 的主导航与 macOS 桌面交互一致。本轮把 EPUB 翻译收敛到和 PDF 相同的左侧工具栏，避免功能重复和概念冲突。新应用图标以 `branding/lumen-icon-source.png` 为唯一源稿，`branding/render.js` 生成标准 iconset 和 `Resources/AppIcon.icns`，构建时再复制到 app bundle。

## 剩余风险与建议改法

1. **验证结果假通过（P1，2026-09-27 已收紧）**：`tools/run_smoke.py` 现在逐项要求成功收据；诊断仅打印前缀、跳过、失败计数或 JSON `pass=false` 都不能通过。全量烟测及缺失收据的反向测试见下方续审记录。
2. **大型 PDF 批注保存卡顿（P1，已修复主要路径）**：≥64 MiB 文件的 Lumen 自有批注按改动页快照，在独立 PDFDocument 的后台任务中串行写入同目录临时文件，校验页数与批注数后原子替换。文档世代号防止旧任务回调新文档；文件指纹防止覆盖外部修改；退出应用时等待在途保存。外部来源批注仍走保守同步路径。以 357.4 MiB / 1058 页扫描 PDF 副本完成新增、连续保存、编辑、删除及外部变更拒绝测试；未找到 ≥500 MiB 的可用样本，故不能声称已覆盖该档位。
3. **EPUB 书内脚本（P1，2026-09-27 已收紧）**：WKWebView 默认禁止正文内容 JavaScript；Lumen 自己的用户脚本仍能运行。测试 EPUB 同时包含 `<script>` 与内联 `onload`，WebKit 实测 `bookScriptBlocked=true`、`appBridgeReady=true`。仍需将恶意 EPUB、远端资源等作为单独的安全边界持续检查。
4. **EPUB 格式覆盖（P2）**：为安全和可预测性，当前拒绝 ZIP64、分卷、加密、链接和解包总量超过 512 MB 的书。这是有意限制。若需扩大覆盖，应优先接入受维护的 ZIP 库并保留当前额度，不要放宽外部命令路径。
5. **会话共享语义（P2，已收紧）**：AI 会话仍是进程级共享；面板持续显示当前文档，跨文档会话额外显示起始文档，并已有一键新建当前文档会话。引用来源校验继续保留。
6. **Swift 6 并发迁移（P2，已完成产品目标）**：两个产品目标均切换 Swift 6 语言模式；存储状态、EPUB 源、网络提供方、PDF/OCR 任务及 AppKit 主线程边界已调整。`swift test --disable-sandbox` 75/75 通过，Debug 与 Release 均构建成功。

## 2026-09-27 续审

本轮优先修复验证假通过和 EPUB 执行边界，并在 AI 面板持续显示当前文档；跨文档继续同一会话时额外显示会话的起始文档。EPUB 冷启动烟测还暴露出 `/private/tmp` 与 `/tmp` 指向同一目录但 WebKit 文件读取授权使用不同 URL 别名的问题，现已将读取根目录与章节 URL 统一解析为同一路径。Release 构建、签名、75 项 Swift 测试、4 项烟测解析测试和 5/5 案例端到端烟测通过；EPUB 回读为 `bookScriptBlocked=true`、`appBridgeReady=true`、`pass=true`。整个修改不触及 PDF 滚动、缩放或面板热路径。

本轮后续验收以 357.4 MiB、1058 页真实扫描 PDF 的副本执行；新建两条批注、修改及删除共四次后台写回均通过，外部文件变更保护也通过。批注提交耗时 4.9 ms，后台保存期间主线程 16 ms 定时器迟到 p95 为 2.1 ms、最大 191.8 ms。该定时器不是显示帧率，最大尖峰仍值得后续真机观察。ZIP64 等 EPUB 扩展仍是有意限制，不属于已知故障。

## 验证记录

- `swift test --disable-sandbox`：75 个测试通过（Swift 6 语言模式）。
- `./build.sh release`：应用组装完成；最终发布包另行复核 `codesign --verify --strict --deep dist/Lumen.app`。
- EPUB 翻译端到端：用模拟 OpenAI 兼容服务打开同时含 `p` 与叶级 `div` 正文的测试 EPUB，左侧翻译面板显示 `3 / 3` 段，页面译文块 3、失败 0、加载中 0。
- PDF 性能：Release 构建下以 120 页文档驱动 60 步连续滚动，主线程停顿 p95 `5.34 ms`，超过 16.7 ms 的样本 `3 / 92`。这些是定时器延迟指标，不是实际显示帧率，不能证明快速滚动流畅。2026-09-22 用户实测仍有严重卡顿，本项尚未验收。随后用真实长篇 PDF、2 倍缩放、120 步滚动复测，关闭侧栏和 AI 面板后，主题/原色两组 CPU 分别为 `29.32 / 29.40 ms/步`，主线程停顿 p95 为 `1.16 / 0.80 ms`，说明主线程延迟低仍可伴随高后台渲染开销；具体瓶颈仍需用户复现与采样确认。已有缩略图暂停措施只解决一部分竞争，不能据此宣称问题已解决。
- 2026-09-27 大 PDF：357.4 MiB / 1058 页的真实扫描件，30 页程序化翻页 p95 在 Debug / Release 两次运行分别为 `2.98 / 6.09 ms`；整页离屏光栅化 p95 为 `17.77 / 21.03 ms`，缩略图缓存均驻留 `160 / 1058` 张。Release 重复遍历内存 `165.7 → 183.9 MiB`（信息性读数）。`thumbnail(of:)` 是内容成本参考，**不是响应式滚动的帧时间**；对应自检已取消这项错误的 60 Hz 断言。两遍有无回调的对照受缓存顺序影响，不能直接作为应用层开销。本轮依用户要求未做真实触控板验收，不据此宣称实际滑动达到某个帧率。
- 2026-09-27 大 PDF 批注：同书副本上连续新增两条、编辑一条、删除一条，四次写回后重开核对通过；文件外部变更后拒绝覆盖通过。后台保存期间 16 ms 主线程定时器迟到 p95 `2.1 ms`、最大 `191.8 ms`；原始 PDF 未修改。
- 图标管线：新 PNG 源稿生成全部 16–1024 pt iconset 和 `Resources/AppIcon.icns`，已随构建复制入 app bundle。
- 本地发布包的 ZIP、SHA-256、构建信息与签名复核保存在 `releases/<version>/`；是否完成远端发布应以 GitHub Release 资产与校验和为准。
