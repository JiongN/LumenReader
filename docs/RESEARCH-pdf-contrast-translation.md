# PDF 逐段对照翻译 · 技术方案调研

> 调研日期：2026-09-21　　状态：**已据此实现并完成首轮验证**
> 目的：回答「Lumen 做 PDF 逐段对照翻译，该走哪条路，是否存在比现方案更好的做法」。

> **实施后的修正（2026-09-21）**：预研建议的页面叠加在真实窗口中会遮盖随后正文，
> 固定版式也无法安全为译文增加高度，因此最终改为“PDF 原页 + 当前页段落对照栏”。
> 默认引擎调整为 Apple 系统翻译，微软在线通道作为后备；Apple 首次使用语言对时由系统
> 下载语言包。下文保留立项时的候选分析，用于解释方案演变，不代表最终界面。

### 已落地的实现与验证

- `PDFLineExtractor` + `PDFParagraphExtractor`：按页面几何、行距、短行和栏块抽段；
  表驱动与真实 PDF 共 42 项通过，真实夹具 2 页、25 行抽出 9 段，字符覆盖率 100.1%。
- `PDFTranslationController`：整本准备、目标语言隔离缓存、取消与迟到结果淘汰；系统翻译
  按最多 24 段批量请求，在线后备沿用已有微软通道。
- `PDFTranslationPane`：只实例化当前页的卡片。真实英文 PDF 已完成 2/2 段英→中翻译、
  缓存落盘和重开命中；原文与译文可选择，PDF 页面没有被修改。
- Apple 通道已拉起系统语言包下载流程；本机未预装该语言对，所以没有把“弹出下载界面”
  误记成翻译成功。微软后备完成了可重复的端到端结果验证。

## 一、结论（先给答案）

**三条结论，按重要性排序：**

1. **不要抄 pdf2zh / BabelDOC。** 它们是 AGPL-3.0 + Python/torch 栈，塞进一个原生 SwiftPM
   应用既踩许可证又踩运行时，而这个项目**连 LICENSE 文件都没有**（`ls LICENSE*` 空命中），
   许可证边界本就模糊 —— 再引入 AGPL 组件会把问题复杂化到没法收场。
2. **翻译引擎采用双轨，但以 Apple Translation 为默认。** 它是系统原生、语言包下载后可离线；
   现有微软网页通道无需配置但依赖未承诺的页面结构，只适合作为后备。首次使用 Apple 语言对
   会出现系统下载提示，这是平台行为而非应用自己的密钥弹窗。
3. **编排层：把 EPUB 那套 `EPUBTranslationController` 的逻辑移植到 PDF 段落模型上，
   不要重写。** 它已经解决了长任务最难的三个问题：可取消、取消后不往新内容里写旧译文、
   批内并发（4）批间串行且顺序可控。PDF 侧要换的只是「段落从哪来、译文写到哪去」这两个注入闭包。

**最终呈现形态：当前页段落对照栏。** 原文与译文在每张卡片中上下成对，整栏位于 PDF 右侧；
PDF 固定版式和交互层保持原样。预研中的页内堆叠经真窗口验证会遮盖正文，已放弃。

## 二、需求拆解：这件事其实是四个独立子问题

「PDF 逐段对照翻译」听起来是一个功能，实现上是四条可以分别决策的链路：

| # | 子问题 | 难点 | 本调研的结论 |
|---|---|---|---|
| 1 | **段落抽取** —— 从 PDF 拿到「一段」而不是「一行」 | PDF 只有字/行级几何，没有段落语义 | 用**行级 bbox 聚类**（缩进 + 行距 + 竖直间隙），不依赖结构化识别 |
| 2 | **翻译** —— 把段落文本变成译文 | 引擎选择、成本、离线、限流 | 双轨：已有必应通道 + Apple Translation（可选） |
| 3 | **呈现** —— 译文画在哪儿 | 叠加层 vs 写回文件 vs 独立视图 | **叠加层**，绝不写回用户的 PDF |
| 4 | **编排** —— 长任务的生命周期 | 取消、换页、进度、部分失败 | 移植 `EPUBTranslationController`，不重写 |

## 三、仓库现状（代码级事实，已逐条核对）

### 3.1 已有：一整套 EPUB 逐段翻译，**PDF 侧完全没有**

| 组件 | 位置 | 事实 |
|---|---|---|
| `MicrosoftTranslator` | `Sources/LumenKit/AI/MicrosoftTranslator.swift` | 必应 `/ttranslatev3` **免密钥**通道。凭证靠抓翻译页 HTML 里的 `params_AbusePreventionHelper` / `IG` / `IID` 四件套，缓存 40 分钟，失败换凭证重试一次 |
| `BingTranslateCredentialsParser` | 同文件 `:195` | 凭证解析单独成类型，**为了能被单测直接喂 HTML**（作者注释写明：这是整条链路最脆弱的一环） |
| `EPUBTranslationController` | `Sources/LumenApp/Reader/EPUB/EPUBTranslationController.swift` | 编排器：批 4 并发、批间串行、可 `stop()`、`loading/done/failed` 三态、占位一次性铺满 |
| 接线 | `EPUBReaderView.swift:27`（`@StateObject`）、`:264`（读目标语言） | 已接线可用 |
| 目标语言设置 | `ReaderSettings.translationTargetLanguage`（默认 `zh-Hans`） | 且外观菜单里有语言选择（`AppearanceMenuButton.swift:241`） |

### 3.2 缺口：PDF 侧零翻译

- `Sources/LumenApp/Reader/PDF/` 下没有任何翻译实现。
- 仓库**尚未使用** `PDFPageOverlayViewProvider`（`grep` 零命中）—— 叠加层是全新的东西，
  不存在「旧实现要拆」的成本，但也没有现成范式可抄。
- PDF 侧已有可复用的文本能力：`usableText(of:)` / `text(around:radius:)` / `fullText()` /
  `hasTextLayer(_:)` / `cachedOCRText(_:)` / `snippet(...)`，以及批注链路的
  `page.string` + `selection(for:)` 几何用法。**段落抽取可以直接长在这些之上。**

### 3.3 当前方案的**真实弱点**（这是用户问「有没有更好的做法」的落点）

必应通道的收益是「零配置、零成本、即时可用」，代价有两处，都必须如实看待：

1. **脆弱**：凭证来自页面 HTML 的正则抓取。作者已在注释里写明「页面结构一变它就会失效」，
   而且**它只承担「尽力而为」的翻译** —— 拿不到凭证就明确报错，不静默返回空串。
2. **无离线能力、无 SLA**：网络不通、被反爬拦、限流（429）都会失败。
   `EPUBTranslationController` 的处理是逐段标 `failed`，不阻塞其余段落。

⇒ 这意味着「更好的做法」不必是「换引擎」，也可以是**加一条不依赖网络的兜底引擎**。这正是结论 2 的来源。

## 五、本轮新做的一手机器实测（推翻了上一轮的一个前提）

### 5.1 前提被推翻：本机是 macOS **26.6.2**，不是 15

```
$ sw_vers
ProductVersion:  26.6.2
BuildVersion:    25G83
```

我上一轮按 `Package.swift:6` 的 `platforms: [.macOS(.v15)]` 推断「本机是 macOS 15」，
**这是错的**：那行是**部署目标**，不是运行系统。修正后结论要跟着改。

### 5.2 但 Vision 结构化识别**仍然用不了** —— 卡在 SDK，不是卡在系统

系统是 26，SDK 却只到 15.5：

```
$ xcrun --show-sdk-version
15.5
$ ls /Library/Developer/CommandLineTools/SDKs/
MacOSX.sdk  MacOSX13.1.sdk  MacOSX14.sdk  MacOSX14.5.sdk  MacOSX15.sdk  MacOSX15.2.sdk  MacOSX15.5.sdk
$ xcode-select -p
/Library/Developer/CommandLineTools        # 没有 Xcode
```

实测结论（三重证据一致）：

| 证据 | 结果 |
|---|---|
| `Vision.tbd` 符号表 | 只有 ObjC 名 `VNRecognizeDocumentsRequest` |
| Vision 头文件目录 | **没有**对应的 `.h`（`grep VNRecognizeDocuments Headers/*.h` 零命中） |
| Swift overlay | **没有** `RecognizeDocumentsRequest` |
| `swiftc -typecheck`（`#available(macOS 26.0, *)` 包裹） | ❌ `cannot find 'RecognizeDocumentsRequest' in scope` |

⇒ **要拿到结构化版面识别，需要的不只是抬高部署目标，而是更新 SDK**
（装 Xcode 26 或更新 CommandLineTools）。这是一条硬约束，写在这里以免下次又白试一遍。

### 5.3 Apple Translation：可编译、en↔zh 受支持、但**模型未下载**

`LanguageAvailability`（macOS 15.0+）在本机 SDK 下**编译通过**，实跑读数：

```
运行系统: Version 26.6.2 (Build 25G83)
  en → zh-Hans: 受支持、模型未下载（首次用会弹下载框）
  zh-Hans → en: 受支持、模型未下载（首次用会弹下载框）
```

⇒ 技术通道成立且免费离线，但**首次使用会弹系统下载框**。
这必须在界面上如实告知（否则用户点一下「翻译」以为坏了）。
按 README 硬约束 5，这是「部分生效必须写清边界」的典型场景。

## 六、推荐管线与分级建议

```
① 段落抽取            ② 翻译            ③ 呈现
行级 bbox 聚类   →   引擎可切换     →   叠加层（不写回）
缩进/行距/间隙        必应 / Apple / LLM   段落堆叠
   ↓                     ↓                    ↓
 [LumenKit 可做]      [见约束 6.1]        [LumenApp]
```

### 6.1 ⚠️ 第一条必须正面回答的约束：翻译调用点落在哪一层

`TranslationSession` **只能通过 SwiftUI 的 `translationTask` modifier 获得**，
且官方文档明确写了：**在挂载视图消失之后继续使用该 session，系统会 `fatalError`**。

这与本项目的分层铁律**直接冲突**：`Sources/LumenKit` 绝不能 `import SwiftUI`。

三条出路，必须选一条并在 ARCHITECTURE 里记决策：

| 出路 | 代价 |
|---|---|
| **A. 翻译调用点放 LumenApp 层**（推荐） | 引擎抽象留一个协议在 LumenKit，Apple 实现放 LumenApp。分层不破，但 Apple 引擎不能给 CLI/引擎层复用 |
| B. 封一个宿主视图专门持 session | 多一层视图生命周期管理，且必须保证翻译期间它不被卸载 |
| C. 不用 Apple，只走 HTTP 引擎（必应 / LLM） | 分层最干净，但放弃离线能力 |

### 6.2 分级建议

| 级别 | 做什么 | 为什么是它 |
|---|---|---|
| **P0** | ① 行级 bbox 聚类抽段落（复用 `usableText` / `page.string`）<br>② 复用现有必应引擎<br>③ `PDFPageOverlayViewProvider` 叠加层呈现 | 全离线**不**依赖新 API、不依赖新 SDK、不写回用户文件；引擎链路已经验证过 |
| **P0** | 把 `EPUBTranslationController` 的编排逻辑移植到 PDF 段落模型 | 逻辑已验证，是复用不是重写 |
| **P1** | 译段缓存（按「文档哈希 + 段落哈希 + 目标语言」存盘） | 翻页回来不重复请求；必应通道有限流，缓存直接降低触发 429 的概率 |
| **P1** | Apple Translation 作为可选第二引擎（按 6.1 的 A 案） | 离线兜底。代价是模型下载引导 + UI 告知 |
| **P2** | 结构化版面还原（段落合并质量、表格、双栏） | **受 5.2 的 SDK 约束，本机现在做不了**。要等 SDK 更新，或外挂 MinerU |
| **P2** | 独立双栏对照视图 | 改动最大，收益不如叠加式 |

### 6.3 呈现形态：为什么推荐「段落堆叠」而不是左右分栏

- **不改变阅读动线**：读过原文的眼睛不用左右扫，译文就在下一行。
- **实现成本低一个量级**：堆叠是在叠加层里「在原文段落下方插一块译文」，
  分栏要同时维护两个滚动容器的同步（对齐、滚动、缩放三套状态）。
- 项目里已有先例证明同步滚动是麻烦事（跨窗口对照阅读那条路要补 `PDFViewportState` 中继）。

## 七、诚实边界（这份调研**没能**回答的）

1. **双栏版面的段落抽取质量未验证。** 本机拿不到可验证的双栏样本
   （见 `docs/VERIFY.md`：像素密度剖面实测用户库三份文档中央 30% 密度均匀 = 全是单栏）。
   所以「分栏版面上段落聚类会不会跨栏合并」**没有实证**，不能假装解决。
2. **`PDFPageOverlayViewProvider` 的实际行为未实测。** 它是新的 API 用法，
   叠加层与主题着色（`ReadingPDFPage.draw` 的整页颜色混合）、与批注图层、
   与缩放/滚动重绘的相互影响，**全部需要真实像素验证**，本轮未做。
3. **Apple Translation 的译文质量未评估。** 只验了「通道成立」，没验「翻得好不好」。
   学术文本的专业术语与公式邻域译文质量，必须人工抽样读。
4. **未做成本估算**（若走 LLM 引擎）。需要按用户真实文档的段数与 token 量实测，
   不能用「大概多少」糊过去。

## 八、明确不做的事

- ❌ **不引入 pdf2zh / BabelDOC 或任何 AGPL 组件。**
- ❌ **不把译文写回用户的 PDF。** 叠加层是内存态，用户点「复制译文」再自己处置。
  （对照：批注是写回原文件的，因为那是**用户明确要持久化**的内容；译文不是。）
- ❌ **不改动 `Package.swift` 的部署目标来换 macOS 26 API。** 抬高部署目标会让老系统用户装不上，
  而本机**连 SDK 都还没有**，改了也编不过。
- ❌ **不在本轮改任何源码**（用户明确要求）。

## 九、如果开工：建议的落地顺序与验证通道

每一批都要能独立编译、独立验证（项目既有纪律）：

| 批次 | 内容 | 验证通道 |
|---|---|---|
| 1 | 段落抽取纯函数（行级 bbox → 段落区间） | 表驱动断言：单栏真实 PDF 上段落数/边界；**反向对照**：故意给一个跨大间隙的行序列，断言不会合并成一段 |
| 2 | 叠加层呈现（先接假译文，不打网络） | `--capture-screen 1` 真像素 + 布局探针（叠加块的位置与原文段落对齐）；**必须验**主题着色与缩放后叠加层不错位 |
| 3 | 接引擎（必应 → Apple 可选） | 桩服务（项目已有 `--mock-ai` 范式）+ 逐段失败态断言 |
| 4 | 译段缓存 | 计时断言：第二次打开同一段**不发网络请求**（跑前后比对请求计数，不是比对耗时） |

**必须回答的一件事（决定 P0 范围）：** 要不要给「翻译」动作配快捷键？
按项目既有原则，**付费动作不给快捷键**；必应通道免费，Apple 也免费，所以可以给。
但若将来接入 LLM 引擎（按 token 计费），必须收掉快捷键。
