二、译文块的四种状态

这四种状态能不能一眼分清，直接决定这个功能好不好用。失败态必须写出原因并给「只重试这一段」——免密钥通道有限流，这是必须有的止损。

四、做这个之前，三条我必须提醒的硬约束

① 段落抽取是本机唯一没验过的一环。整行高亮那轮我实测发现：page.selection(for:) 不按矩形横向裁剪（中线缝宽恒为 0.0），selectionForLine(at:) 在两栏版面上左右栏返回完全相同的 bounds。这些 PDFKit 行为会直接影响段落聚类。你库里的文档实测全是单栏，所以单栏能过；分栏版面本机拿不到可验证样本。
② 结构化版面识别（表格 / 段落合并）本机做不了。你系统是 macOS 26.6.2，但本机 SDK 只到 15.5（没有 Xcode，只有 CommandLineTools），Vision 的 RecognizeDocumentsRequest（macOS 26.0+）编不出来——我实跑 swiftc -typecheck 报 cannot find in scope。要拿它得更新 SDK，不是抬部署目标。
③ Apple Translation 通道实测成立，可作离线兜底。LanguageAvailability 在本机 SDK 下编译通过并实跑读数：en→zh-Hans 与 zh-Hans→en 都是「受支持、模型未下载」——首次使用会弹系统下载框，界面上必须如实告知。且它的 TranslationSession 只能从 SwiftUI 的 translationTask 拿到，与「LumenKit 不许 import SwiftUI」冲突，调用点只能落在界面层。

五、建议的开工方式

先做第一批：段落抽取纯函数 + 表驱动断言。不打网络、不改界面、不动你的 PDF。

  • 先在 text.pdf 与你几份真实论文上量出「抽出来的段落」对不对（段落数、边界、有没有把页眉页脚混进去）；
  • 这一关不过，后面叠加层与引擎全是白搭；
  • 过了再决定引擎（必应主 + Apple 兜底）与呈现细节。
