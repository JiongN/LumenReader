## 1. 设置完善 · 动效 · 快捷键

### 1.1 动效

**选型：全局动效门（MotionGate）+ 令牌转发，调用点零改动**

现状 `DS.Motion.panel/quick/content/hover` 是 `static let Animation`，散落十余处 `withAnimation(DS.Motion.*)`。
把它改成 `static var`，内部转发到 `MotionGate`：

```
DS.Motion.panel → MotionGate.resolve(base: .spring(...))
                    ├─ 用户关闭动效 → .linear(duration: 0)
                    ├─ 系统「减弱动态效果」开启 → 降级为 .easeOut(0.001) + 只保留透明度
                    └─ 速度档（紧凑 0.7× / 标准 1× / 舒缓 1.4×）→ 按倍率重采样
```

新增令牌：`reveal`（入场）、`theme`（主题过渡）、`palette`（命令面板）。

**具体动效清单**

| 场景 | 处理 |
|---|---|
| 侧栏 / AI 面板开合 | 已有 spring；补「宽度变、内容不甩」——内容用 `opacity` + 4pt 位移，不用 `move(edge:)` 全宽位移 |
| 文档打开 / 关闭 | 欢迎页 ↔ 阅读页交叉淡入 + 0.985→1 缩放；内容位图就绪前不显示，避免"先亮后定位" |
| 划词浮动条 | 上浮入场 + 4pt 下沉出场，`spring(response: 0.22)` |
| 主题切换 | 外壳（侧栏/AI 面板/工具条）颜色 `easeInOut(0.25)` 过渡；**阅读内容层不参与**（PDF 重绘会闪） |
| 页码数字变化 | `contentTransition(.numericText())` |
| 侧栏页签切换 | 内容交叉淡入（`easeInOut(0.18)`），不动画页签底条 |
| 命令面板 | 遮罩淡入 + 卡片 0.96→1 缩放弹入 |
| 批注落笔 | 高亮从选区中点向外"生长"（scale 0.6→1 + opacity） |

**关键约束**
- SwiftUI 的隐式动画（`.animation(_:value:)`）、系统 List 折叠、`NSMenu` 展开**不受 MotionGate 控制**。文档要如实说明，不能承诺"一处开关全静音"。
- 默认尊重 `NSWorkspace.shared.accessibilityDisplayShouldReduceMotion`——这是 HIG 要求，且比应用自己的开关优先级更高。
- 动画绝不能进入阅读区滚动路径（滚动事件里 `withAnimation` 是掉帧第一杀手）。

### 1.2 字体与行距

**选型**
- `ReadingFontFamily` 从固定枚举 → **系统字体族选择**：`NSFontManager.shared.availableFontFamilies`，用 `NSFont` 过滤出正文可用字体，按"衬线 / 无衬线 / 等宽 / 圆体"分组。
- 设置页给**带实时预览的选择器**（下拉 + 搜索 + 一段中英混排样例文字）。
- 界面字体与阅读字体**分设**：`uiFontFamily` / `readingFontFamily`。
- 行距：`lineHeight`（已有）扩展为 `1.2 … 2.4`，并新增 `letterSpacing`（字距）、`textAlign`（两端对齐 / 左对齐）。

**关键约束（必须如实告知用户，否则是欺骗性设计）**
- **EPUB**：走 WKWebView/CSS，字体族、行距、字距、对齐全部生效。
- **PDF**：正文是固定排版。字体与行距设置**只影响外壳 UI（侧栏 / AI 面板 / 设置页）与 AI 对话可读性**，不改变 PDF 正文。要替换 PDF 正文字体需要重写内容流（`page.draw` 重建 + 字体子集嵌入），代价与风险都超出本轮范围。
- 字体列表里会混进图标字体、符号字体（`Apple Color Emoji` 等），必须过滤，否则选中后正文变方块。
- 字体名要写进 CSS 时需处理含空格/引号的族名。

### 1.3 深色主题与窗口外观（已实现，含一个必须记住的坑）

**需求**：选「深夜」时侧栏、AI 面板、工具条要一起暗下来，不能出现"近黑正文区旁边贴着亮白面板"。

**实现**：`AppearanceProbeView`（`Sources/LumenApp/Design/WindowAppearance.swift`）把外观设到
**`NSApp.appearance`**，而不是 `NSWindow.appearance`。

**为什么不能设 `NSWindow.appearance`（实测记录，踩过）**：

```
11.301 [探针] 已设置窗口外观：darkAqua
11.397 [探针] updateNSView isDark=true           ← 此刻窗口仍是 darkAqua，看着像成功了
14.731 [Lumen] app=nil window=nil effective=Aqua ← 3 秒后 SwiftUI 把它抹回 nil
```

设置动作本身是成功的，但**随后被 SwiftUI 重置**。症状极具误导性：`--capture` 截图里侧栏依旧是浅色，
而阅读区背景已经变暗——一半生效一半没生效。中间还排查过两个错误方向，记在这里避免重走：
截图方法本身没问题（`cacheDisplay` 对材质确实不可靠，但这次不是它）；PDF 页中央取到 `#FFFFFF` 也不是 bug
（那是纸面，主题只改画布底色）。

**排查手段**：`--capture` 时会把 `NSApp.appearance` / `window.appearance` / `effectiveAppearance` /
按该外观解析出的系统色一起打进日志，再用 `tools/sample_pixels.swift` 对截图取色比对亮度。
这条"日志 + 客观取色"的路子比肉眼看截图可靠，后续视觉改动都按这个来。

**PDF 纸面的取舍（有意的，不是遗漏）**：深色主题下 PDF **纸面仍保持白纸**，只把纸面四周的画布压暗
（`pdfCanvasBrightness`）。理由：反相纸面会同时反相书里的照片、图表与插图，把一本带图的书变成底片。
需要长时间夜间读纯文字 PDF 的用户，用画布压暗 + 降低屏幕亮度即可。若后续要做"反相纸面"，
必须是独立开关 + 明确提示"会反相图片"，不能跟主题绑在一起。

## 2. 提示词库（多种提示词 + 管理）

**选型**
- 模型 `PromptTemplate`：`id / name / icon / content / scope / builtIn / createdAt / useCount`。
- `scope`：`selection`（划词）/ `unit`（本节）/ `document`（全书）。决定它出现在哪个入口。
- 占位符只支持三个：`{selection}` `{document}` `{locator}`。不做表达式/脚本。
- 存储 `PromptStore`（`prompts.json`），首次启动写入内置模板。
- 内置 10 条（内置项可改内容但不可删，只能"停用"）：
  复述要点 / 找出论证漏洞 / 解释术语 / 写成文献笔记 / 生成讨论问题 / 提取研究方法 /
  译成英文 / 压缩到 200 字 / 列出可反驳的反例 / 与我的研究方向建立联系。
- 入口三处：划词条「更多」菜单、⌘K 命令面板（按名字搜索）、AI 面板空状态（按 scope 过滤）。
- 管理入口：设置 → AI → 提示词（增删改、排序、启停、恢复内置、导入导出 JSON）。

**范围**：中。不含多轮模板（模板 → 连锁提问）与变量条件。

**关键约束**
- 模板正文**只能拼进 user 消息**，系统提示（`PromptLibrary.systemPrompt`）永远前置且不可被模板覆盖——否则模板变成提示注入入口。
- 模板内容长度上限 4000 字，超长截断并提示。
- 模板渲染后仍走原有上下文预算裁剪（`PromptLibrary.truncate`），不能让一条长模板把原文挤掉。

## 5. 高亮与批注

### 5.1 PDF —— 采用 PDF 标准标注

**选型**
- 使用 `PDFAnnotation` 的标准 markup 类型：`highlight / underline / strikeOut / squiggly / text(便签) / freeText`。
  **这是唯一能让 Preview、Acrobat、Zotero 都认的正确做法**——自绘图层只在 Lumen 里看得见，等于把用户数据锁在应用里。
- 4 色（黄 / 绿 / 蓝 / 粉），颜色随阅读主题微调饱和度（深色主题下浏览器默认高亮色过亮）。
- 批注文字写入 `annotation.contents`（PDF 标准字段，其他阅读器可见）。
- 侧栏新增「批注」页签：按页分组、点击跳回、编辑批注、删除、导出。
- 导出三种：Markdown 清单 / CSV / **带标注的 PDF**（`PDFDocument.write(to:)`）。

**关键约束**
- `.burnInAnnotationsOption` **绝不能开**：它把标注烧进内容流，之后不可再编辑，且文件体积暴涨。
- 加密 / 只读 PDF 无法写回 → 需捕获失败并降级为"仅本会话可见 + 导出时另存"。
- 写回原文件前必须自动备份（应用内 `backups/`，每文件保留 1 份），因为 PDF 大文件在坚果云/OneDrive 同步目录下，写回会触发同步。
- 单页标注超过约 200 个时 `PDFView` 渲染明显变慢 → 需在设备上实测后设阈值提示。

### 5.2 EPUB —— 旁挂 JSON

EPUB 内无处安放标注（重写 XHTML 会破坏 EPUB 结构与签名）。
- 存储 `docs/<hash>/annotations.json`，锚点 = `chapterIndex + 元素锚(path/id) + charOffset + 15 字文本指纹`。
- 指纹用于容错：文本变了（换译本）也能尽量重新定位；定位失败则标为「失效锚点」并保留文本，不静默丢弃。
- 渲染：WKWebView 注入高亮 span（复用现有 `__lumen` 桥）。
- 导出：与 PDF 同一套 Markdown / CSV。

### 5.3 统一侧栏与检索

- 批注列表与「搜索」页签并列，支持按颜色/类型/关键字过滤。
- ⌘K 面板新增：`高亮选中` / `加批注` / `导出全部批注` / `跳转到下一条批注`。

**范围**：大。第一版覆盖 高亮 / 下划线 / 删除线 / 便签批注 / 侧栏管理 / 导出 Markdown+PDF。

## 6. AI 阅读模式：多文档对比

### 6.1 形态

**选型：独立「对比」窗口，不替换主阅读视图**

理由（第一性原理）：多文档对比的核心是"看差异"，不是"精读某一本"。因此：
- 对比视图**不装载 PDFView**，只取文本 + 缩略图 → 规避 3~4 个 PDFKit 文档同时驻留的内存与渲染开销（大书单份 100~300MB）。
- 原始精读仍在主窗口，对比窗口负责"发现 → 定位 → 提问"，定位后一键在主窗口打开对应页。

### 6.2 对齐（对比的地基）

没有对齐，对比就是"三段各自无关的文字并排"，AI 也只能给出泛泛而谈。

- **自动对齐**：把各文档的目录（PDF outline / EPUB nav）或首段摘要喂给 LLM，
  让模型输出「章节对应表」JSON。这是不用嵌入模型也能做到语义对齐的实用路径。
- **手动对齐**：并排滚动 + 「锁定当前单元为同一组」。
- 对齐结果可保存，形成**对比工作区**（`comparisons.json`：文档列表 + 对齐表 + 对话）。

### 6.3 三个视图

1. **并排原文**：2~4 栏，各自独立滚动，对齐行高亮联动。
2. **AI 差异分析**：给定一组对齐单元，输出
   - 共识 / 分歧 / 各自主张 / 证据缺失
   - 每条结论必须带来源标注（`[文档A §3]`），可点击跳回
3. **对比对话**：上下文 = 当前对齐组的各文档文本，可追问。

### 6.4 关键约束（全部是真实风险）

| 约束 | 说明 |
|---|---|
| 上下文预算 | 3 文档 × 8 节 × 2000 字 ≈ 48k 字符，超直接预算 → 必须走 map-reduce，复用现有 `summarizeDocument` 的同构逻辑 |
| 检索仍靠关键词 | 无嵌入模型、不联网建索引。跨文档检索 = 各文档 `retrieveProvider` 结果合并去重后按分数排序 |
| 对齐质量 | 目录结构差异大的文档（一本有 30 章、一本只有 5 节）自动对齐会失败 → 必须提供手动兜底，且失败时要明说"对齐不可靠"，不能让模型假装对齐了 |
| 跨文档引用 | `DocumentLocator` 目前不含文档标识 → 需扩展为 `(documentID, locator)`，否则引用跳回会跳错书 |
| 内存峰值 | 文本提取串行（一次一个文档），避免 4 个 PDF 同时解析 |
| 语言混杂 | 中英混排对比时，提示词要显式声明"保留原文术语，不要只在中文层面比" |

**范围**：大（本轮最大一块）。建议分两步：先「2 文档 + 差异分析 + 对话」，再「4 文档 + 工作区保存」。

## 7. 扫描版 OCR → 写入可检索文本层

### 7.1 现状与目标

现状：识别当前页 → 结果弹层 + 缓存供 AI 使用（**会话内可见**）。
目标：把识别结果以**不可见文本层**写进 PDF，产出**可检索 PDF**——能搜索、能选中、能复制、能被其他工具使用。

### 7.2 选型

逐页用 `CGContext(consumer:)` 重建：
```
for page:
  beginPDFPage([kCGPDFContextMediaBox: 原页 mediaBox])
    page.draw(with: .mediaBox, to: ctx)          // 原图，视觉完全不变
    ctx.setTextDrawingMode(.invisible)            // render mode 3
    for line in OCRLines:
      在 line.box 映射出的页面矩形内，用 CJK 字体绘制 line.text
  endPDFPage()
```
- Vision 返回的 bbox 已是归一化坐标（左下原点），映射到 PDF 用户空间只需 `x*w, y*h, dw, dh`，无需坐标系转换。
- 字号：按 bbox 高度推定；横向不匹配时用 `context.textMatrix` 做水平缩放，保证选中范围与图像对齐。
- 字体：必须显式用 CJK 字体（`PingFang SC` / `Songti SC`），否则写进去的是方块——搜索也搜不到。

### 7.3 范围与交互

- 三种粒度：本页 / 指定页范围 / 全书（后台任务 + 进度 + 可取消）。
- 输出**新文件**（`原名.ocr.pdf`），**绝不覆盖原文件**：原扫描图不可再生，风险不对称。
- OCR 结果缓存到 `docs/<hash>/ocr.json`，重跑不重复识别。
- 设置项：`仅写入置信度 ≥ 0.5 的行`（默认开）、`识别语言`（中英 / 纯中文 / 纯英文）。

### 7.4 关键约束

- 页面旋转（`page.rotation ≠ 0`）必须处理，否则文本层与图像错位。
- 页码 / 页眉误识别会污染全书搜索 → 提供"跳过页边 5% 区域"选项。
- 全书 OCR 耗时：2 倍图 `.accurate` 约 1~3 秒/页 → 300 页需 5~15 分钟。必须在设置里明确告知预期耗时，并支持中途取消。
- 生成的可检索 PDF 体积会增大（文本层很小，但用 `page.draw` 重建会丢弃原文件的对象复用）→ 需实测，若膨胀明显则改走"在原 PDF 上追加内容流"的增量写法（PDFKit 不直接支持，需 `CGPDFDocument` + 底层 API，列为备选）。

## 8. 全文 PDF 翻译（BabelDOC 思路的原生实现）

**目标**：把一本外文 PDF 整本译成中文，且**保留原版面**（图表、公式、页码、脚注位置都不动）。

### 8.1 为什么不直接调 BabelDOC

BabelDOC（PDFMathTranslate 的下一代）是 Python 工具链（`pymupdf` 版面分析 + `doclayout-yolo` 模型 + ONNX 推理）。
在 Swift 应用里嵌一套 Python 运行时 + 一个几十 MB 的版面检测模型，代价是三件事同时发生：
打包体积、启动时间、以及"模型文件放哪、怎么保证不被杀"的运维复杂度。

**采用它的架构思想，不采用它的运行时**：

```
BabelDOC：  版面分析 → 分块翻译 → 按原坐标渲染 → 双语对照 PDF
Lumen 版：  PDFKit 段落提取 → 段落级 LLM 翻译（带缓存） → CGContext/CoreText 重排 → 输出新 PDF
```

差别只在第一步：BabelDOC 要跑模型才发现"哪里是段落"，而 **PDF 本身已经带着精确的文本坐标**
（`PDFSelection.bounds`），段落切分用行距/缩进规则就能做——这是 DESIGN.md 里 OCR 版面还原用过的同一套办法。
省掉整个模型，也就省掉了打包与启动的代价。

### 8.2 选型

- **段落提取**：`PDFPage.selection(for:)` 逐行取 `bounds`，按行距阈值 / 首行缩进 / 字号变化合并成段；公式与表格区域**整体跳过**（检测到大量短行 + 大间距即判定为图表区，不翻）。
- **翻译**：复用现有 `OpenAICompatibleProvider`，**段落级**批量调用（每批 8~12 段，段间用编号分隔），**不是整页一次性**——整页一次会让模型合并段落、丢公式编号。
- **渲染**：`CGContext(consumer:)` 生成新 PDF，逐页 `drawPDFPage` 重绘原页（矢量方式，不栅格化），再把译文用 **CoreText** 排上去。
- **缓存**：`docs/<hash>/translations.json`，key = `sha256(原文段落) + 目标语言`。改目标语言才失效，重开文档秒出。

### 8.3 两种形态（用户已确认：可切换的两层）

| 模式 | 实现 | 取舍 |
|---|---|---|
| **双语对照**（默认） | 新页宽度 = 原页宽 ×2，左半 `drawPDFPage` 原页，右半排译文 | 无重叠风险，对照阅读体验最好；缺点是横向变宽，需要左右滚动或整页缩小 |
| **原位覆盖** | 新页 = 原页，译文按原段落 rect 排 | 版面最忠于原书；但中文比英文短/长不定，必须在段落框内自适应字号 |

**原位覆盖的防溢出规则**（不做这一步会得到一页叠字）：
在段落 rect 内从 `原字号` 起逐步缩小（下限 0.62×），仍塞不下则按行截断并追加 `…`，
同时在段落右下角画一个可点开的脚注标记，指向完整译文。**宁可截断，不做重叠。**

### 8.4 范围

- 只支持**文本型 PDF**。扫描件必须先跑第 7 章的 OCR（走 `usableText(of:)` 即可自动兼容）。
- 触发粒度：**当前章 / 全书**两档。全书是后台任务，带进度与取消。
- 输出**新文件**（`原名.zh.pdf`），**绝不覆盖原文件**——与第 7 章同一原则。
- 不做：术语表、翻译记忆库、公式重排（`LaTeX` 重建）、图文混排重排（reflow）。

### 8.5 关键约束

- **成本必须先告诉用户**：一本 300 页的书约 1200~2000 段，按每批 10 段 = 120~200 次请求。动工前在 UI 上给出预估段数与请求数，用户点了才开始。
- **段落合并是质量的第一杀手**：译文与原文必须**双向可定位**（点译文跳到原文段落），所以每段的结果要单独存，不能只存整页译文。
- **失败要能续**：某一批请求失败不能丢掉整本进度，缓存里已成功的段落必须保留，重跑只补失败批次。
- **字体**：译文必须显式用 CJK 字体（`PingFang SC` / `Songti SC`），否则写进 PDF 的是方块。
- **不计入本轮验收的是"翻译质量"**：质量取决于用户自己配的模型，本轮的验收标准是**版面正确 + 可定位 + 可续跑 + 不覆盖原文件**。

## 横向：性能预算（首要要求，不能被新功能破坏）

| 风险点 | 对策 |
|---|---|
| 全书 OCR 阻塞主线程 | 渲染在主线程（PDFKit 非线程安全）、识别在后台、结果分批写盘、全程可取消 |
| PDF 翻译重复调用 | 段落级翻译缓存 `docs/<hash>/translations.json`，改目标语言才失效 |
| 批注数量影响渲染 | 每页标注数阈值提示；批注列表虚拟化 |
| 对比视图内存 | 串行提取、不装 PDFView、及时释放文本缓冲 |
| 动画掉帧 | 阅读区滚动路径内禁止动画；面板动画只动 transform/opacity，不动 layout |
| 大文档内存 | 已有 `.singlePageContinuous` 模式保持；不为新功能引入全文常驻缓冲 |
