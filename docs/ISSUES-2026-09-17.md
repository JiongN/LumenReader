## 1. ✅ 全屏后显示/动作异常；退出 zoom 后无法返回页面

### 排查思路

沉浸模式同时牵扯两套状态：**SwiftUI**（`isImmersive`、面板可见性、正文限宽）与
**AppKit 窗口**（`.fullScreen`）。定位这类问题先问两件事：谁在改状态？谁在监听状态？

于是 grep 全仓 `didEnterFullScreen|didExitFullScreen|styleMask|toggleFullScreen`。

### 根因

**R1（主因）状态单向、没有回程。** 全仓搜索只有 `AppState.swift:278-279` 两行命中，
**没有任何地方监听 `didExitFullScreenNotification`**。App 只做「沉浸 → 全屏」这一半；
用户从系统侧退出全屏（绿灯 / 菜单 / `⌃⌘F`）时 `isImmersive` 永远停在 `true`——
面板收不回、正文一直限宽、**工具栏被 `.toolbar(.hidden)` 锁死**。
这同时是第 6 项「工具栏不见了」的根因，两个问题同源。

**R2 快捷键与系统撞车。** `KeyBindings.swift:253` 把 `toggleImmersive` 绑成 `⌃⌘F`——
**正是 macOS 系统全屏的标准组合**（也是 SwiftUI `WindowGroup` 自动生成的菜单项）。
按一次两个 toggle 同时触发，状态机各自翻转。

**R3 两段动画并行。** 布局动画（弹簧 0.34s）与系统跨 Space 全屏动画（约 0.5s）同帧启动，
互相抢帧、布局被反复重算——这就是「动作效果异常」。

**R4 可能作用于错误窗口。** 原 `applyFullScreen` 用 `NSApp.keyWindow`，刚点过设置窗口就会打错对象。

### 修复

| 改动 | 文件 |
|---|---|
| 新增窗口探针：记主窗口 + 监听全屏进出通知 | `Sources/LumenApp/Design/WindowStateProbe.swift`（新建） |
| `systemFullScreenChanged(_:)`：退出全屏 → 复位沉浸 | `Sources/LumenApp/AppState.swift` |
| `driveFullScreen(_:animated:)`：进入时把全屏推到布局动画之后 | 同上 |
| `resolvedWindow()`：优先用探针记录的主窗口 | 同上 |
| 默认组合键 `⌃⌘F` → `⌥⌘F` | `Sources/LumenKit/Store/KeyBindings.swift` |
| 挂载探针 `.windowState(state)` | `Sources/LumenApp/RootView.swift` |

**设计要点：只处理「退出全屏」一个方向。** 全屏可以脱离沉浸单独存在（用户直接按系统全屏，
面板工具栏都该留着）；但反过来不行——退出全屏而不复位，用户没有任何路径回到正常界面。

### 验证

新增开关 `--exit-fullscreen-after N`：进沉浸 N 秒后**绕过应用逻辑**直接 toggle 窗口全屏
（全程不碰 `isImmersive`），复现用户那条路。

```
--immersive 1 --exit-fullscreen-after 3：
  [immersive] 收到全屏通知 isFullScreen=true  当前 isImmersive=true
  [layout]    窗口内容区 1440x900，共上报 1 项          ← 沉浸布局生效
  [immersive] 模拟前：isImmersive=true 侧栏=false AI面板=false
  [immersive] 模拟系统方式退出全屏（未触碰 isImmersive，当前=true）
  [immersive] 收到全屏通知 isFullScreen=false 当前 isImmersive=true
  [immersive] 已随退出全屏复位：isImmersive=false 侧栏=true AI面板=true   ← 修复前不可能出现
```

## 3. ✅ 主题切换缓慢；去掉全黑主题

### 根因

**R1 同一次切主题被做了两遍。** `Reader/EPUB/EPUBReaderView.swift` 原有两条 `onChange`
（`of: reader` 与 `of: theme.id`），而 `ReaderSettings` **里就包含 `themeID`**，
换主题必然同时触发两条 → 两次 `evaluateJavaScript` 注入 CSS 变量。

**R2 动画作用域过宽。** `RootView.swift` 的 `.animation(DS.Motion.theme, value: theme.id)` 挂在
`Group` 上，覆盖面是整棵子树——注释写「不往下碰阅读内容」，实现却把 `ReaderContainerView`
（内含 PDFView / WKWebView）卷进了动画事务。

**R3 `NSApp.appearance` 的全应用重解析。** `Design/WindowAppearance.swift` 设的是应用级外观，
会让所有窗口与所有 `NSVisualEffectView`（侧栏、AI 面板的材质）重新解析。这一步**必要**
（否则深色下侧栏还是白的），是「慢」的主要来源，属固有成本，只能减少触发次数（已有去重）。

### 去掉纯黑主题

`ReadingTheme.all` 移除 `.oled`（`#000000`）。**但枚举 case 必须保留**：直接删掉的话
`themeID: "oled"` 解码失败 → 容错解码兜成 `.paper` → **深色用户下次打开变成纸白**，
这是最糟的降级方向。

| 改动 | 文件 |
|---|---|
| `all` 去掉 `.oled`；`theme(for:)` 走 `.migrated` | `Sources/LumenApp/Design/ReadingTheme.swift` |
| 新增 `ReadingThemeID.migrated`（`oled → midnight`） | `Sources/LumenKit/Store/Settings.swift` |

| 命令面板 `ReadingThemeID.allCases` → `ReadingTheme.all` | `Sources/LumenApp/CommandPalette/CommandPaletteView.swift` |

## 4. ✅ 解释「连不上 127.0.0.1:8777」

### 出处与含义

`Sources/LumenKit/AI/OpenAICompatibleProvider.swift` 的 `translateTransportError`，
命中 `NSURLErrorCannotConnectToHost` / `CannotFindHost` 时抛出。
请求 URL 由同文件 `endpoint("/chat/completions")` 拼出。

含义：App 向**当前激活的服务商**发 `POST {baseURL}/chat/completions`，
**在建立 TCP 连接阶段就失败**——不是 401/404 那类服务端应答，是根本没连上。

### 你的实际情况（实证）

本机 `settings.json` 的 provider 列表：

```
[0] 本地桩服务  id=11111111-1111-1111-1111-111111111111
    baseURL = http://127.0.0.1:8777/v1   model = mock-chat
[1] DeepSeek    id=F211A0CA-…            ← 当前激活
[2] DeepSeek    id=648DD651-…
```

`8777` 是本项目**自检用桩服务端口**（`tools/mock_openai_server.py`）。
当前激活的是 DeepSeek，所以现在不会遇到；但把「本地桩服务」设为活动服务商、
而桩服务没在跑，每次请求都必然弹这条。

> 补充：这条 provider 是**你自己在设置页加的**，不是自检写进去的——
> `--mock-ai 1` 写入的名字是「桩服务（自检）」且用随机 UUID，并且只改内存。

### 常见成因

1. 选错了服务商：选了本机服务（127.0.0.1 / localhost / Ollama 11434）但本地没启动。
2. 端口写错或漏写。
3. 本地服务（Ollama / LM Studio / 自建网关）没启动，或监听的不是 127.0.0.1
   （例如只听 IPv6 的 `::1`、只听局域网网卡）。
4. 少写 `/v1`（`endpoint()` 只对少数已知域名自动补）。
5. 代理 / VPN 把 127.0.0.1 也劫持了（少见但真实）。

### 排查步骤

```bash
# 1. 看当前用的是哪个服务商：AI 面板头部 chip，或「设置 → AI」的活动项
# 2. 端口上有没有服务在听
curl -s -m 3 http://127.0.0.1:8777/v1/models     # 连不上就是没服务
lsof -nP -iTCP:8777 -sTCP:LISTEN                 # 看谁在监听
# 3. 若确实要做自检：python3 tools/mock_openai_server.py 8777
# 4. 若不需要：设置里切回真实服务商，或删掉这条
```

### 顺带的产品改进

原文案只说「连不上 X」，没告诉用户**当前用的是哪个服务商**——而读到这条提示的人
多半已经忘了自己选的是哪一项。现在错误信息带上服务商名，并对本机地址额外点一句
「需要本机有服务在监听 / 若你并不想用本机服务，去设置换一个」。

### 现状（修复前）

### 实现

**两个设计决定：**

- **模板的系统提示是「整段替换」而不是拼接**。模板的意义就是换一种读法
  （「批判性审读」与「严谨学术解读」的立场并不相同），把两段立场不同的指令拼在一起，
  模型只会两头都不满足。读者背景（`persistentMemory`）仍然保留——那是「谁在读」，与「怎么读」无关。
- **「默认」是模板菜单里的第一个选项，默认选中**。默认行为是经过调校的，
  套模板是在它之上做加法，所以「不加东西」必须是一眼看得到、随时回得来的选项。

**顺带修的隐患**：内置模板原本用 `UUID()` 生成 id，而 `presets` 是计算属性——
每次取都得到一组新 id，用户上一轮选中的模板下一轮就找不到了。已改成写死的 UUID。

## 8. ✅ 钥匙串授权框反复弹出

### 现象

每重编译一次，应用启动 / 渲染 AI 面板时就会不断弹钥匙串授权框。

### 排查思路

弹的是**系统**授权框（「Lumen 想要使用您存储在钥匙串中的机密信息」），
不是应用自绘的界面——全仓检索 `.alert` / 自建卡片，没有任何索取密钥的弹窗。
所以问题不在「应用想跟用户要什么」，而在「应用去读钥匙串时被系统拦了」。

于是要回答两个问题：**为什么会被拦**，以及**为什么是"一直"**。

#### 第一步：两个查询通道的授权成本不一样（探针实测）

写了个探针（`LAContext.interactionNotAllowed = true`，把「会弹窗」变成「直接失败」，
因此全程不打扰用户），对同一条真实密钥分别走两条路：

| 查询 | 状态 | 耗时 | 结论 |
|---|---|---|---|
| 只读属性（`kSecReturnAttributes`） | `0` 成功 | 32ms | **不需要授权** |
| 读密文（`kSecReturnData`） | `-128` 被取消 | **7282ms** | **触发系统弹窗** |
| 只读属性（允许 UI） | `0` 成功 | 80ms | 属性通道永不弹窗 |

结论：**判断「有没有配密钥」根本不需要密文，但 `hasKey` 去解密文了。**
`AIKeychain.hasKey` 原本是 `read(account:) != nil`，而 `read` 带 `kSecReturnData`。

#### 第二步：为什么"一直"弹

两个放大器叠在一起：

1. **调用点在 SwiftUI 渲染路径上。** `AISetting` 的 `isConfigured`
   （`AITypes.swift:108`）被 `AIPanelView.providerMenu`（`AIPanelView.swift:100-102`）
   求值——`providerMenu` 是 `private var`，每次 body 重建都会算一遍。
   而 `SecItemCopyMatching` 是**同步阻塞**调用，弹窗期间主线程被按住。
   截图回归时一次跑 14 个实例，每个实例若干次渲染 → 弹窗连发。
2. **ad-hoc 签名的身份就是 CDHash。** `./build.sh` 每次产出新 CDHash
   （实测 `c0333f43…` → `3997c211…`），而 login 钥匙串的 ACL 认的正是二进制身份，
   于是旧条目在新二进制眼里是「陌生程序」。已复现：重新签名后
   `SecItemAdd` 返回 `-25299`（重复项），读回返回 `-128`（需授权）。
   条目自身的 `mdat == cdat`，说明**从未有任何二进制被写进它的 ACL**。

### 修复

`Sources/LumenKit/AI/AIKeychain.swift`：

1. **`hasKey` 改走属性查询**——不带 `kSecReturnData`，不解密，故不走 ACL 授权。
   这是本次修复的核心，也是文件里最需要被守住的一条实现约束。
2. **加进程内缓存（三态）**：`value`（密文已在内存）/ `present`（条目存在、密文未取）/
   `missing`（已确认不存在）。渲染路径上的重复求值成本降为 0。
   - `hasKey` 命中 `present` 即可返回 true，不必再打钥匙串；
   - **只缓存「确实不存在」**，授权被拒 / 用户取消这类失败不缓存——
     缓存了就等于把一次拒绝升级成本进程内的永久拒绝。
3. `save` 成功后把明文直接写进缓存，省掉紧随其后的一次授权。

### 未来如果要动这块，先看这四条实测边界

为避免重复踩坑，三条"看起来更彻底"的路都已经试过并排除：

| 方案 | 实测结果 |
|---|---|
| 改用**数据保护钥匙串**（`kSecUseDataProtectionKeychain`） | `-34018` 缺 entitlement 被拒 |
| 给 ad-hoc 签名**补 entitlement** 以走通上一条 | 进程被内核 **SIGKILL**（受限 entitlement 需配 provisioning profile） |
| 换成**稳定签名身份**（不随 CDHash 变） | 本机 `security find-identity -v -p codesigning` = **0 个身份**，需新建自签证书（等于让用户多做一套设置） |

所以：**「重编译后首次真正用到密钥时会弹一次」是当前签名条件下的地板，不是没优化完。**
点「始终允许」后同一次构建内不再弹。要抹掉它只能引入稳定签名身份，
或在条目 ACL 里信任所有应用（安全降级，未采纳）。

### 验证

新增 `--keychain-report 1`（只读查询，不写不删用户钥匙串）。
断言不看终值——`hasKey` 走属性通道还是密文通道返回的都是同一个 Bool——
只看**耗时与钥匙串调用次数的增量**：

```
冷启动首次判断：存在=true 耗时=29ms（预算 500ms）
账户 F211A0CA…  存在=true  首次=0ms  再次=0ms  钥匙串调用+0  缓存=已缓存「存在」
账户 11111111…  存在=false 首次=3ms  再次=0ms  钥匙串调用+1  缓存=已缓存「无」
账户 648DD651…  存在=false 首次=1ms  再次=0ms  钥匙串调用+1  缓存=已缓存「无」
对照：不存在的账户 00000000…  存在=false  钥匙串调用+0  缓存=已缓存「无」
自检：通过 8 项，失败 0 项 ✅
```

决定性的是这一行：**在全新 CDHash `3997c211…` 上，`hasKey` 判定 `存在=true` 只用 29ms
且不弹窗**。修复前这条路径是读密文，实测需授权并耗时 7282ms。
「再次=0ms / 调用+0」则证明缓存生效。

冷启动计时特意打在**当前激活的服务商**上——AIPanelView 渲染路径求值的就是它，
拿一个没人用的服务商去测，测的不是真实路径。
