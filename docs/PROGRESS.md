### 这一批踩到的坑

1. **自检通道被自己并发污染**。`didFinish` 会为同一份 DOM 触发多次（`--jump-to`
   先落第一章再跳章），两轮自检同时改 `--lm-paged` / `--lm-columns` 互相覆盖——
   实测「一次翻页跳了两个视口宽」（2696 = 2×1348）。已加互斥锁与

2. **读数恒为 0 ≠ 没问题**（本族第二次）。短文档 `maxScroll=0`，翻页分支整段跳过，

3. **`columnCount` 在连续流下是 `auto`**，`Number('auto')` 得到 NaN，

## 本批次（第五批）：修 P1「窗口缩小后面板宽度不被重新钳制」

### 缺陷是怎么被发现的

QA 独立验证第四批时实测（用户当前真实配置，无构造输入）：

- `--window-size 920x620`（就是应用的最小窗口）→ `readerSurface w=266.5pt < 320pt`；
- 更极端：宽窗口下把两侧拖到 420 / 547，再把窗口缩到 920 → `readerSurface w=0`、
  `sidebarRail x=-97`（图标栏被推出屏幕左缘）、`aiPanel maxX=1017` 越出右缘。

用第一批的构建同样能复现，所以**不是**第二批引入的回归；但「阅读区保底 320pt」
是本批引入的承诺，必须闭环。

**根因**：动态上限只在**拖拽提交那一刻**参与计算。窗口被拉小之后没有任何一次
提交，落库的旧宽度原样参与布局——钳制没有第二次生效的机会。

### 修法：显示宽度与落库宽度分开

```
落库宽度（settings.ui.*）   ← 只有用户主动拖 / 双击 / 设置页才会变
        ▼ 每次布局重算（PanelWidthPolicy.resolve，纯函数，不写设置）
显示宽度（panelLayout.*）→ .frame(width:)
```

于是窗口变窄时显示自动收窄、拉回时偏好自动还原，落库值始终只在用户主动操作时变。

分配顺序（`预算 = 容器宽 − 图标栏 − 分隔线`，`可用 = 预算 − 阅读区保底`）：

1. 装得进「可用」→ 各按需求给；
2. 装不进 → **被钉住的一侧足额拿**（不拖动时钉侧栏，拖动时钉被拖的那一侧），
   对侧吸收差额但不低于自己的下限；
3. 连两侧下限都装不下（容器 < 534pt）→ 下限优先，阅读区让位（降级，已写进
   `ARCHITECTURE.md` 的「已知边界」）；
4. 最后一道闸：两侧之和不得超过预算——**图标栏 x 永远 ≥ 0**。

与「两侧等比压缩」的偏离（QA 建议的是等比）：等比会让「写入 X → 渲染 X」在窄
窗口下失效（写 266 只渲染 225，拖到底松手反而更窄），而钉住一侧是**不动点**
（结果再喂回算式还是同一组值），这是「拖完不弹回」的数学保证。侧栏优先的理由
也写进了架构文档：结构化列表 vs 会自己重排的正文。

### 自检：`--resize-report` 6 项 → 12 项

新增的六条，全部做了人为破坏验证：

| # | 断言 | 破坏方式 → 结果 |
| - | ---- | --------------- |
| ⑤ | 最挤状态下阅读区仍 ≥ 320 | 删掉渲染时重算 → 红（实际 166pt / 0pt） |
| ⑥ | 最挤状态下侧栏被压到落库偏好以内 | 同上 → 红 |
| ⑦ | 最挤状态下图标栏完整落在窗口内 | 同上 → 红（`x=-97.0`，与 QA 独立复现的数字一致） |
| ⑧ | 收窄窗口不改写落库的偏好 | 加一个覆盖式写回 → 红（落库 420 → 266） |
| ⑨ | 窗口拉宽后侧栏回到落库偏好 | 同上 → 红（实渲染 266，期望 420） |
| ⑩ | 极窄容器下两侧面板不超出预算 | 删掉最后那道等比压缩的闸 → 红（占用 480 > 预算 446） |

两条写法上的坑（都踩到了，已修）：

- **必须走一遍真实的「宽 → 窄 → 宽」**。第一版停在窄窗口上读一次数，
  覆盖式钳制那种实现根本没被触发，⑧⑨ 是恒真的。
- **「最挤状态」要把两侧偏好都顶到静态上限**（52+2+420+640 = 1114 > 920）。
  只顶侧栏的话总宽仍装得下，⑦ 会退化成恒真。

「极窄窗口」这一档改成了**算式层**断言：实测脚本把窗口设成 700pt 也会被
SwiftUI 拉回 920（`.frame(minWidth: 920)` 持续兜住 NSWindow 的 minSize），
界面到不了比最小窗口更窄的尺寸。

## 已知的、故意的取舍

- **智能目录的下限在「结构」而非「理解」**：它靠每页开头 260 字推断分节。
  一本正文没有任何小标题、且每页开头都是同一句话的文档，它给不出有意义的目录。
  这比「假装能读懂」诚实。
- **摘要不预生成**：只看用户点开的那几节。整本 300 页的逐节摘要会很贵，
  而多数人只关心其中两三节。
- **`usableText` 的 24 字符门槛**：AI 上下文里宁可这页什么都不给，
  也好过把「12」这个页码当成正文——但对「复制全文」用的是另一套规则，
  因为那边少一格正文比多一个页码严重得多。
